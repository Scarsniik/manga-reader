# Source linking

Mangas downloaded from a scraper store their origin with:

- `sourceKind: "scraper"`
- `scraperId`
- `sourceUrl`
- optional `sourceChapterUrl` and `sourceChapterLabel`

The library card action **Voir source** opens the configured scraper on the stored source when the scraper still exists. If the scraper was deleted, the same action opens `sourceUrl` in the system browser.

On a scraper details page, the download button changes to a redownload action when a matching library manga is already linked to the current source. Redownloading keeps the existing manga entry and replaces only the local image files in its folder.

Search result cards and scraper bookmark cards expose the same standalone download action when the scraper has `Fiche` and `Pages` configured without chapter linking. The card action uses the download icon; it switches to the linked yellow state when a local manga already matches the scraper source.

The scraper bookmarks view can filter saved cards by text, including title, source, author and tag text, detected bookmark languages, page count range and reading status. A tri-state `Series` control uses each source title parser to detect chapter numbers: left-click keeps only parsed series entries, while right-click hides later chapters but retains standalone titles and chapters 0 or 1. Its **Comptages** menu opens separate modals for frequent tags and frequent authors, each with a minimum occurrence threshold and a current-selection/all-scope switch. The active modal computes its statistics in a worker so large bookmark collections do not block the interface. That worker keeps a bounded session cache keyed by bookmark scope and source identity: unchanged bookmarks reuse their parsed authors and author-name compatibility checks, while additions, edits and removals only resynchronize the affected cache entries. Tags keep their optional fuzzy grouping, and tags already linked through the same tag favorite are merged automatically even when fuzzy grouping is disabled. Author groups reuse the author-correspondence name matching rules and author-favorite aliases. Each author row shows a fixed-size cover selected from one of its associated bookmarked manga without increasing the row height. Bookmark metadata also retains author-page URLs extracted from details pages. Each scraper's configured title parser supplements missing bookmark author metadata, with conservative bracket extraction only as a fallback. Clicking an author name applies it to the bookmark text filter. Its separate **Vue combinée** action opens those retained author pages immediately, while the standard (non-advanced) author-correspondence search completes missing pages in the background; middle-click opens the same combined view in a workspace tab. Clicking a tag still applies it to the bookmark text search, while middle-clicking the tag opens the filtered bookmarks in a workspace tab. When a bookmark has no detected language but its scraper has exactly one configured source language, that source language is treated as the bookmark manga language. The reading status uses the scraper reader progress when available, then falls back to the explicit card read marker stored in the view history. The same view has a **Rescraper les bookmarks** action that reloads every saved bookmark through its current scraper details configuration and saves newly found metadata, including languages and linked author pages.

Multi-source search and author favorites also expose reading status filters. In merged result mode, the filter applies to the whole merged card instead of individual sources: a matching card is displayed with all its sources, and a non-matching card is hidden entirely. A merged card is considered read when at least one source is completed, in progress when no source is completed but at least one source has progress, and unread otherwise.
Merged result cards include a compact read toggle next to the reading progress block. When one or more sources are in progress, marking the card as read only writes a read marker for those in-progress sources. When no source has started, the read marker is written only on the first source. Clearing the read state removes only the explicit read markers already written by that toggle.
Clicking an in-progress block opens the scraper reader directly on the saved page for that source. When the progress belongs to a chapter-based reader, the card resolves the matching chapter before opening the reader.

Search result cards and scraper bookmark cards also write a compact view history in `collections.sqlite` under the Electron `userData/data` folder. By default, a write requires at least 80% of the card surface to stay visible in the viewport for 1 second; both the visibility percentage and dwell duration are configurable in the application settings. A card is identified by `scraperId` plus its source URL when available, otherwise by `scraperId`, title and thumbnail, then only the compact id, scraper id, optional source URL, first seen date and optional read date are persisted. Cards absent from history when the current list is loaded keep a green border for that list session, even after the viewport dwell writes them to history. Opening a scraper details page stores a temporary snapshot of the listing state, so browser/back navigation restores the same first-view display instead of recalculating it from the persisted history. Cards already present in history use the default border, and cards marked with the read button get a grey border. Result grids that record this history expose a **Non vus seulement** filter. Its membership is frozen while the filter remains active, so a card does not disappear when its viewport dwell is recorded; the history is evaluated again when the filter is reactivated or the result view changes. A merged card is included when at least one of its sources was unseen at that evaluation point. Correspondence-review cards are excluded because those cards intentionally do not write view history. By default, the history keeps seen-only records for 45 days, read records for 365 days, and caps the collection at 5000 records. These three cleanup values are configurable in the application settings, and `0` disables the corresponding cleanup. Seen-card batches use a single SQLite transaction and update only the affected rows. Existing `scraper-view-history.json` data is imported transactionally on the first database launch and the legacy file remains untouched as a migration backup.

Scraper bookmarks and reader progress use the same local database. Bookmark saves, removals and read-state updates are incremental, and renderer windows receive the changed record when possible instead of reloading the complete collection. Duplicate-bookmark detection keeps the existing title, author, sequence and romanization rules, but uses indexed URL, exact-title and fuzzy-length keys to shortlist candidates before the final comparison.

Scraper search, homepage, author, tag and multi-source cards reuse that same candidate index to warn when a result probably corresponds to a bookmark, a read/in-progress manga or an item from a saved reading list. This includes the shared virtualized grid used by merged search results, combined author/tag views, favorites and latest results. Series checks reuse the tolerant manga-correspondence title analysis, including its extraction of authors, translated titles, trailing metadata and numeric chapter, volume or part markers. Named subtitles remain exclusive to manga-correspondence result grouping and never trigger these global alerts. A later entry from a series already present in the reading history receives a `Série commencée` tag with the latest known sequence. A sequenced entry with no completed current or earlier reading receives a visible `Précédents non lus` tag; bookmarking it from the details page or Quick Review also asks for confirmation. A completed range such as chapters `1-8` counts as a reading match for each contained chapter. Virtualized multi-source grids prefetch matching several viewports beyond the smaller DOM rendering overscan, in viewport-distance order, so warning-induced card measurements normally settle before the card becomes visible without mounting all prefetched cards. Exact bookmark and read identities for any source carried by a merged card keep their existing card controls and are not repeated as potential warnings. The details page and listing cards share the same potential-match pipeline and menu implementation. When card enrichment has loaded the details page, matching and exact bookmark/read identities use its canonical title and final URL while the card keeps its listing title for display. Card menus use the combined presentation, display match covers, aggregate duplicate targets, add optional reading/bookmark/list badges, and render through a high-level portal above regular card controls. Listing checks run in bounded animation-frame chunks, then advanced Japanese romanization refines the result asynchronously. Matching waits for the current candidate snapshot and carries forward semantically valid cached results while a new snapshot loads, avoiding a transient badge removal and duplicate first pass. Results are cached per semantic card fingerprint, so focus, clicks, menu state, virtualized layout changes, seen-only view-history writes, details-history writes and search-history writes do not rerun matching; only a new or changed card, an actual reading/bookmark/list candidate change or a matching option invalidates the relevant cache. The loading indicator is likewise scoped to cards that are actually being checked. The warning menu can open the matching source normally or in a workspace tab. The `scraperCardPotentialMatchesEnabled` setting controls these checks and defaults to enabled.

The scraper details page also provides:

- **Lier a un manga** / **Changer le lien**, to attach the current scraper source to an existing local manga through a searchable cover grid. When the source was already linked to another manga, validating a new selection clears the previous link.
- **Ouvrir dans le navigateur**, to open the current source URL outside the app.
